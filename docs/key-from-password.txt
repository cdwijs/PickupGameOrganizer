Suppose I can't store anything on the device. Everything comes from the username+password. What is the most secure way to use username+password to decrypt something  that is shared across nodes?       

● Short version: the constraint "nothing on the device" almost always still permits storing salt + wrapped-key metadata alongside the ciphertext in the shared storage. That's the pattern real password
  managers (Bitwarden, 1Password, Standard Notes) use, and it's near-optimal.

  Case A — you can store metadata with the ciphertext (recommended)

  Even if the device is stateless, the ciphertext lives somewhere. Put per-user auxiliary data next to it. Nothing here needs to be secret.

  Stored in shared storage, keyed by username:
    salt         : 16 random bytes
    wrapped_DEK  : AES-GCM(KEK, DEK)   # DEK is a random 32-byte key
    ciphertext   : AES-GCM(DEK, data)  
 
  Device workflow (only username + password in hand):
    1. Fetch { salt, wrapped_DEK, ciphertext } by username
    2. KEK = Argon2id(password, salt, t=3, m=256MiB, p=1)
    3. DEK = AES-GCM-decrypt(KEK, wrapped_DEK)
    4. data = AES-GCM-decrypt(DEK, ciphertext)
    
  Why this is strong:
  - Random salt defeats precomputed/rainbow attacks and cross-user parallelism (each user must be attacked independently).
  - Argon2id with a high memory cost (256 MiB+) crushes GPU/ASIC brute force. Tune t/m to whatever your slowest supported device can bear.
  - Wrapped DEK means password changes only re-wrap 32 bytes, not the whole blob. Also lets you rotate the DEK without knowing the password (if you ever need multi-device sharing).
  - AEAD (GCM) gives integrity, so the server can't tamper.
  
  Threat model: a full shared-storage breach yields the salt + wrapped_DEK + ciphertext. Attacker must run Argon2id per password guess per user. With memory-hard parameters and a decent password, offline
   attack is expensive.

  Case B — truly nothing but username + password + ciphertext bytes

  If auxiliary metadata is also forbidden (rare; ask why), you lose the random salt and the wrapped DEK. Best you can do:

  salt = SHA256("myapp-v1|" || normalize(username))   # domain-separated, deterministic
  key  = Argon2id(password, salt, t=4, m=512MiB, p=1) 
  data = AES-GCM-decrypt(key, ciphertext)             # nonce lives inside the ciphertext blob
 
  Notes on the compromises:
  - Deterministic salt from username — same weakness as before: attacker can precompute per known username. Argon2id's memory cost is your only defense; crank it.
  - Normalize the username (Unicode NFC, lowercase, trim) so trivially different inputs produce the same key. Otherwise users get locked out by an iOS autocap.
  - Domain-separation prefix ("myapp-v1|") prevents cross-protocol collisions if the same username+password is reused elsewhere with a similar scheme, and gives you a version tag for future migrations.
  - Password change = full re-encrypt. No way around it without stored metadata. 
  - Pepper trick: if you have an app binary or a server the device talks to, a static "pepper" (secret constant) mixed into the salt raises the bar for anyone who only stole the ciphertext store. Not a
  device secret, but not universally known either.
 
  Add a PAKE if a server is in the loop
 
  If the device fetches the ciphertext from a server, don't send the password (even hashed) to authenticate. Use a PAKE — OPAQUE is the modern choice. It gives you:
  - Password-authenticated key exchange without ever revealing the password (or a password-equivalent) to the server.
  - The server stores an OPAQUE "envelope" that also functions as your wrapped-DEK carrier — you fold Case A into the login flow.
  - Resistance to precomputation attacks even if the server is fully compromised.

  This is what you want if the "shared across nodes" part is a server you also control.
  
  Practical picks

  - KDF: Argon2id, memory ≥ 256 MiB, iterations ≥ 3, parallelism 1. Fall back to scrypt (N=2^17, r=8, p=1) only if Argon2 is unavailable. Avoid plain PBKDF2 unless a compliance regime forces it.
  - Cipher: AES-256-GCM or XChaCha20-Poly1305. Random 96-bit nonce (GCM) or 192-bit (XChaCha) stored with the ciphertext.
  - Username normalization: NFC + casefold + trim.
  - Version byte on every blob so you can migrate KDF params later.
 
  Bottom line: the answer is Case A — Argon2id-derived KEK wrapping a random DEK, with salt + wrapped_DEK stored next to the ciphertext. That satisfies "nothing on the device" while keeping proper
  salting and key-rotation properties. Case B is what you fall back to only if the shared storage genuinely can't hold per-user metadata, and it's meaningfully weaker.

❯ what is wrapped_DEK?                                                                                                                                                                                     

● DEK = Data Encryption Key. The key that actually encrypts your data.
  KEK = Key Encryption Key. A key whose only job is to encrypt other keys.
  wrapped_DEK = the DEK, encrypted with the KEK. 
 
  "Wrapping" is just a naming convention for encrypting a key with another key. The wrapped form is safe to store in the open because you need the KEK to unwrap it.

  Why bother with two keys?

  Naive design — password directly encrypts the data:
  key  = Argon2id(password, salt)
  blob = AES-GCM(key, data) 
 
  Problems:
  - Password change re-encrypts everything. New password → new key → must decrypt+re-encrypt the whole database. Painful if it's large.
  - Can't share across devices/users without sharing the password itself.
  - Can't rotate the encryption key independently of the password.
 
  Two-key design — password protects a random key that protects the data:
  DEK          = 32 random bytes                    # generated once, at account creation
  KEK          = Argon2id(password, salt)           # derived from password each login
  wrapped_DEK  = AES-GCM(KEK, DEK)                  # stored alongside ciphertext
  blob         = AES-GCM(DEK, data)                 # stored alongside wrapped_DEK
  
  Now:
  - Password change = derive new KEK, re-wrap the 32-byte DEK. The big blob is untouched.
  - Multi-device sharing = give another device the DEK (over a secure channel), or wrap the same DEK with a second user's KEK.
  - Key rotation = generate a new DEK, re-encrypt the blob once, done. Doesn't affect passwords.
  - Compromise isolation = if you ever need to revoke a device's access, you rotate the DEK.
 
  Concrete example

  Account creation:
  password    = "correct horse battery staple"
  salt        = random(16)                = 0x8f3a...
  KEK         = Argon2id(password, salt)  = 0x2c91...
  DEK         = random(32)                = 0xa47e...
  wrapped_DEK = AES-GCM(KEK, DEK)         = 0x5b02...  ← store this
  blob        = AES-GCM(DEK, "my secrets") = 0xf19c... ← store this
  Server stores: {salt, wrapped_DEK, blob}. No password, no KEK, no DEK.
  
  Login on a fresh device:
  fetch(salt, wrapped_DEK, blob)
  KEK = Argon2id(entered_password, salt)
  DEK = AES-GCM-decrypt(KEK, wrapped_DEK)   # fails with wrong password
  data = AES-GCM-decrypt(DEK, blob)
 
  Password change from "old" to "new":
  KEK_old         = Argon2id("old", salt)
  DEK             = AES-GCM-decrypt(KEK_old, wrapped_DEK)
  salt_new        = random(16)
  KEK_new         = Argon2id("new", salt_new)
  wrapped_DEK_new = AES-GCM(KEK_new, DEK)
  store(salt_new, wrapped_DEK_new)          # blob untouched
 
  That's the whole idea. "Wrapping" just = "encrypting a key with a key." The pattern is called envelope encryption and it's how AWS KMS, Google Cloud KMS, LUKS, Bitwarden, 1Password, and essentially
  every serious system does password-derived encryption.
